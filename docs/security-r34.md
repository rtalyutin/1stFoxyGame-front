# R3/R4: целевая проверка границ доверия и сохранения

Отчёт ниже фиксирует локальные воспроизведения и исправления на момент review. Последующая независимая браузерная проверка, PostgreSQL 18.6 (38 PASS без пропусков, включая обрыв записи после убийства) и CI упакованной пары завершены; точные версии и границы доказательства находятся в [verification.md](verification.md). Это дополнение не расширяет review до полного аудита зависимостей или production.

Проверка выполнена `/root/r34_review` для согласованного приложения, локально, на синтетических аккаунтах через явную инъекцию `MemoryRepository`. Внешние системы, реальные учётные записи и продакшен не затрагивались. Область: серверная авторизация, повтор операций, продвижение серверной симуляции, кошелёк, восстановление повреждённого забега и доступ второго клиента после завершения. Это не полный аудит приложения.

`handoff_schema=FEATURE_HANDOFF/1`, `handoff_digest=880ed9d2dc0004f39250f4a5c3739840cc1f9c4b37edf78b652dc787f5aa44e4`; feature `R3/R4-no-graphics`, потребители: координатор, backend/frontend owners, независимая QA. Основание: запрос «Реализуй релиз 3 и 4. Без графики» и `r34-front/docs/r3-r4.md`. Результат для проверенных исправлений — `VERIFIED`; решение — `CONTINUE`. Данные в PostgreSQL остаются типизированными EAV; технический журнал и снимок не являются заменой кошелька. Статически проверены parameterized SQL, привязка профиля/забега/receipt к session account, отрицательный путь чужого account, атомарное сохранение профиля + снимка + receipt, BigInt GoldMilli и отказ на переполнение. Клиент не принимает команду начисления награды: награда следует из серверного replay. Эти выводы относятся к прочитанному коду, а не к измеренной долговечности БД.

Ограничения: локального PostgreSQL нет; не проверялись production-конфигурация, реальные устройства, нагрузка, полный dependency audit. `trustProxy=false` сохранён осознанно: за прокси общий IP limiter 100/min плюс limiter 5/min на логин, цепочка доверенных production-прокси ещё не настроена. Это не подтверждение готового production-rate-limiting для индивидуальных IP.

## Финальная адресная перепроверка новой версии

После сигнала владельца каталога о завершённой регенерации миграции повторены REVIEW-01/02/03/05 и положительный Origin+Host с портом: **PASS локально** на указанных ниже исходниках. Проверены неизменяемость runtime-каталога, отказ дробному/отрицательному/переполняющему GoldMilli и дубликатам вида врага; точное равенство SQL миграции 004 результату `economySeedSql()`: **PASS**.

Проверка новых `RunView.loot` и записей `StoredRun`:

- Серверный replay синтетического сильного врага начислил `20000` milli и один компонент одновременно в кошелёк и добычу забега; счётчик убийств равен 1.
- Повтор идентичного operationId вернул исторический receipt, не увеличив кошелёк/добычу второй раз.
- Крафт уменьшил текущий кошелёк, сохранив валовую добычу забега; завершение сохранило её; новый забег начал с нулевой добычи.
- Переполнение только добычи забега отклонило всю операцию: профиль, снимок и журнал receipt остались прежними, новый receipt отсутствует.

Все эти сценарии — **PASS локально**. SQL колонки `loot_*`, чтение/UPSERT, ограничения и общий BEGIN/COMMIT прочитаны; реальная SQL транзакция/перезапуск не исполнялись этим проверяющим и требуют CI. Runtime-награды берутся из глубоко замороженного `content/rewards.json`; EAV каталог представляет ту же версию через сгенерированную миграцию. Произвольное изменение каталога в работающей БД не является поддерживаемым runtime override: новые значения выпускаются с новой версией контента/миграцией/сборкой. Readiness проверяет наличие миграций, метаданных и текущих шести definitions; точное соответствие источника и seed проверяется сборочным gate.

Первый дополнительный loot fixture ошибочно расположил врага за линией поражения (`z=-4`): симуляция корректно завершилась с `breach`, награды не было. Fixture исправлен на врага впереди (`z=4`, aim `z=1`) до выполненного положительного сценария. В промежутке редактирования генератора наблюдалось несовпадение SQL; после сигнала STABLE и регенерации точная parity прошла. Эти setup/active-edit отказы не классифицированы как дефекты продукта.
