# R1: тестовый адрес и откат

Файлы готовят доставку двух проверенных образов на отдельный адрес. Хостинг, домен, доступ к серверу и TLS пока не выбраны; это не инструкция о состоявшемся выпуске. R1 не содержит runtime БД и не требует секретов. Авторизация и постоянный профиль появятся в R3.

## Что должно быть известно до первого запуска

- Отдельный сервер или контейнерная среда с Docker Engine и Docker Compose v2.
- Домен, DNS, способ выпуска/обновления TLS-сертификата и доступ к настройке внешнего HTTPS reverse proxy.
- Одобренная пара front/back: Git SHA, успешный `R1 verify`, конкретный Actions run и артефакт. Артефакты непроверенных PR в staging автоматически не продвигаются.
- Кто выполняет выпуск, где хранятся текущий и предыдущий env-манифесты и архивы образов.

## Подготовка артефактов

Скачайте выбранный **frontend CI-артефакт**: он содержит оба образа, которые прошли совместный smoke-тест. Отдельный backend CI-артефакт полезен для проверки бэка, но не заменяет образ из проверенной пары. В каталоге распакованного frontend-артефакта выполните:

```sh
sha256sum -c SHA256SUMS
docker load -i image.tar.gz
docker load -i backend-image.tar.gz
docker image inspect --format '{{.Id}}' "$(cat image-id.txt)"
docker image inspect --format '{{.Id}}' "$(cat backend-image-id.txt)"
cat source-sha.txt backend-source-sha.txt
```

Контрольные суммы подтверждают целостность скачанного пакета; источник подтверждайте URL/run/SHA в GitHub. Команды `inspect` должны вернуть ровно значения из `image-id.txt` и `backend-image-id.txt`. Для запуска используйте ID, а не изменяемый тег. Не запускайте `docker build` при продвижении уже проверенного артефакта.

Скопируйте `release.env.example` в локальный `releases/<идентификатор>.env` рядом с `compose.yml` и заполните `FRONT_IMAGE`/`BACK_IMAGE` проверенными ID. Этот файл не содержит секретов. Сохраните выбранные архивы и метаданные отдельно: Actions удаляет их через 14 дней. Не удаляйте предыдущую рабочую пару.

## Запуск

Из каталога `deploy`:

```sh
docker compose --env-file releases/<идентификатор>.env -f compose.yml config --quiet
docker compose --env-file releases/<идентификатор>.env -f compose.yml up -d --wait --wait-timeout 60
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/api/v1/health
curl --fail http://127.0.0.1:8080/version.json
```

`/healthz` проверяет frontend; `/api/v1/health` проходит через тот же nginx в backend и должен вернуть `status: "ok"`, `apiVersion: "1"` и время сервера. nginx проксирует `/api` внутри контейнерной сети, поэтому браузер обращается к тому же origin. Backend не публикует порт на хосте. Значение `revision` в `/version.json` должно совпадать с `source-sha.txt`; пара backend SHA/image ID берётся из того же frontend-артефакта.

По умолчанию frontend слушает только `127.0.0.1:8080`. На выбранном хосте настройте внешний HTTPS reverse proxy на этот адрес, с редиректом HTTP → HTTPS. Конфигурация сертификата зависит от выбранного провайдера и здесь намеренно не подменяется фиктивным доменом. Если внешний proxy находится в другом контейнере, сначала согласуйте его сеть и адрес привязки; не открывайте backend в интернет.

После настройки домена проверьте HTTPS на реальном устройстве, отсутствие mixed content, успешный `/api/v1/health`, запуск забега, паузу после разрыва сети и возобновление только явным действием. Сравните работающие image IDs:

```sh
docker compose --env-file releases/<идентификатор>.env -f compose.yml images
```

Зафиксируйте адрес, время, пару SHA/image IDs и результат проверки. Только после этих шагов можно считать O04 выполненной. Одна зелёная CI-проверка не подтверждает доступность адреса, TLS или поведение браузера.

## Откат

Используйте сохранённый env-файл предыдущей проверенной пары:

```sh
docker compose --env-file releases/<предыдущий>.env -f compose.yml up -d --wait --wait-timeout 60
curl --fail http://127.0.0.1:8080/api/v1/health
```

Повторите проверку HTTPS и запуска игры. Образы не пересобираются. В R1 нет миграций БД или сохранённых профилей, поэтому восстановление данных не требуется. Если это первый выпуск и предыдущей версии нет, безопасный откат — остановить эту пару командой `docker compose --env-file releases/<идентификатор>.env -f compose.yml down`; страницу следует считать недоступной, пока дефект не исправлен.

Не запускайте `docker image prune` до завершения окна отката. Для будущих релизов с БД этот порядок должен быть дополнен совместимостью миграций и восстановлением данных.
