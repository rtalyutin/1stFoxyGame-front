# Поставка R3/R4 без графики

Репозитории содержат реализацию и CI. Этот документ не подтверждает обновление рабочего сервера. Перезапуск контейнера запускает прежний image ID; обновление требует загрузить новый проверенный комплект, применить миграцию и заменить оба image ID.

## Комплект

Использовать один успешный frontend CI artifact: `SHA256SUMS`, `release.json`, `image.tar.gz`, `backend-image.tar.gz`, оба `*-image-id.txt`, оба `*-source-sha.txt`, `deploy.tar.gz`. `release.json` связывает точные source SHA и image IDs обеих сторон; те же значения печатаются в CI для проверки комплекта. Frontend закрепляет backend в `deploy/backend-ref.txt`. Проверка сравнивает каталоги и весь код симуляции обеих сторон. Новые модели, текстуры и VFX не создаются.

```bash
sha256sum -c SHA256SUMS
gzip -dc image.tar.gz | docker load
gzip -dc backend-image.tar.gz | docker load
tar -xzf deploy.tar.gz
```

Записать image IDs в отдельный локальный `release.r34.env`. Сохранить прежние IDs и compose/env для возврата. Секреты и содержимое файлов учётных данных не входят в артефакт.

## База и доступ

При переходе с R2 сохранить тот же compose project name и volume PostgreSQL. `compose.r34.yml` намеренно сохраняет имя проекта `foxy-r2`. Если рабочая поставка использовала другое имя/volume, указать его явно; не создавать пустую БД вместо существующей. PostgreSQL наружу не публикуется.

До смены приложения сделать резервную копию и проверить восстановление в отдельной БД. Поддерживается PostgreSQL 18, миграции `001`, `002`, `003`, `004`, `005`; CLI проверяет контрольные суммы и повторное применение. R3/R4 добавляет профиль и технические журналы, сохраняя каталог R2. Миграция `005` добавляет версии баланса и защиту протокола записи забегов; её установка требует согласованной новой пары приложения.

Подготовить разные подключения мигратора и `foxy_runtime`. Пароль роли задаёт оператор вне репозитория. Файлы URL для Node-контейнеров должны читаться UID 1000 (например, владелец 1000:1000 и режим 0400 в закрытом каталоге); file-backed Compose secrets сохраняют права исходного файла. После миграции применить `runtime-grants.sql` от мигратора: приложение получает работу с профилями и журналами, без DDL и изменения аккаунтов/паролей. В backend монтируется только runtime URL; мигратор доступен отдельным одноразовым контейнерам. Схема приложения — `public`; подключение к чужой/немигрированной среде должно провалить readiness.

## Аккаунты

Публичной регистрации нет. PR на backend должен содержать только согласованные стабильные `accountId` и `login`, цель среды и проверку повторного применения. Пароли, хэши, токены и подключения не включать в PR. Учётные данные передаются владельцу отдельно.

На защищённой машине подготовить JSON-массив `{accountId,login,password}` в файле `0600` или `0400`, затем локальным backend CLI:

```bash
node dist/profile/hash-cli.js --input-file /protected/plainaccounts.json --output-file /protected/accounts.json
```

Результат содержит scrypt-хэши. Для bind mount файл должен читаться UID 1000 контейнера и сохранять режим `0400`/`0600`; Docker secrets с режимом `0444` для этого CLI не подходят. Применить от мигратора:

```bash
docker compose --env-file release.r34.env -f deploy/compose.r34.yml --profile migrations run --rm migrate
docker compose --env-file release.r34.env -f deploy/compose.r34.yml --profile accounts run --rm provision
```

Повтор provision сохраняет существующий пароль, кошелёк, предметы и забег. Замена пароля — отдельный `password-cli.js --rotate --file` с защищённым `{accountId,password}`; она отзывает прежние сессии. Сессия живёт 30 дней, cookie HttpOnly/SameSite=Strict/Secure в production. Внешний HTTPS обязателен для production входа; локальный HTTP используется только явным тестовым runtime.

## Переключение и проверка

1. Остановить записи старой пары и зафиксировать резервную копию.
2. Запустить PostgreSQL, применить миграции, runtime grants и согласованную миграцию аккаунтов.
3. Запустить backend, проверить `/readyz` внутри контейнера. Она возвращает 503 при недоступной БД/схеме.
4. Запустить frontend из той же пары; сверить `/version.json`, label backend и оба source SHA.
5. Через HTTPS войти в выданный аккаунт, начать/приостановить/восстановить забег, проверить профиль после перезагрузки. Крафт доступен только в добровольно посещённом магазине; UI не меняет кошелёк до ответа сервера.

```bash
docker compose --env-file release.r34.env -f deploy/compose.r34.yml up -d postgres
docker compose --env-file release.r34.env -f deploy/compose.r34.yml up -d backend frontend
```

Ошибка или timeout операции проверяется по прежнему operationId. Перед перехватом управления второй клиент читает; явный takeover приостанавливает забег и запрещает запись прежнему клиенту. Нет фонового боя/дохода при offline. Неподдерживаемый snapshot завершает только забег, имущество остаётся.

## Возврат и копии

Для установок до миграции `005` при возврате переключить оба образа на прежние IDs, не удалять volume и не откатывать таблицы профиля разрушительными командами. После `005` старый backend не имеет совместимого протокола записи, а старый клиент не понимает новые снимки `r34.2`: обычное переключение на прежнюю пару не является допустимым откатом. Порядок установки и восстановления редактора описан в [BALANCE.md](BALANCE.md). R2 не использует R3-профиль; его игровой прогресс не переносится обратно. Для возврата с восстановлением данных сначала проверить копию в отдельной БД; не восстанавливать поверх работающей базы вслепую.

`backup-r34.sh` делает атомарный custom-format dump в закрытый каталог. Расписание, RPO/RTO, срок хранения и внешнее хранилище задаёт оператор; автоматическая задача на рабочем сервере здесь не установлена. CI проверяет восстановление аккаунта, ресурсов, экипировки, операции и snapshot в отдельной тестовой схеме. Production время восстановления пока не измерено.

Диагностика: контейнерные журналы содержат request/operation/run IDs и код ошибки, без пароля, cookie и полного профиля. При 503 остановить клиентскую запись, проверить readiness, миграции и доступ к БД. Не заменять проблемный профиль пустым.

## Изменение баланса после установки

[Редактор `/admin/balance/`](BALANCE.md) позволяет менять весь числовой и булев баланс Runner без новой сборки или перезапуска. Право редактора выдаёт оператор существующему аккаунту, по умолчанию оно отсутствует. Публикация сохраняет целую неизменяемую версию; новый забег получает её, начатые и сохранённые забеги удерживают прежние правила, цены и награды. Начальный интервал появления магазинов — ровно 250 м пробега. Для первого включения механизма необходимо один раз установить совместимую пару и миграцию `005`.
